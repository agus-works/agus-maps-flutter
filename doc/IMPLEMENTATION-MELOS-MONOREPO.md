# Melos Monorepo Implementation Notes

## Goals

- Convert the repository to a Melos-managed Pub Workspace.
- Copy `agus-design` into the repository without using a git submodule.
- Keep `agus_design` fast and independent from DuckDB, CoMaps, map assets, and native plugin builds.
- Let `example/` inherit `agus_design` when building the map example.
- Update CI dependency setup so workspace package resolution does not break GitHub Actions.
- Document the new structure and Widgetbook workflow under `doc/`.

## Workspace configuration

The root `pubspec.yaml` now defines the workspace:

```yaml
workspace:
  - example
  - packages/agus_design
  - packages/agus_design/example
  - tool/skin_generator_tool
  - widgetbook
```

The root plugin remains at `.` and is included in Melos with:

```yaml
melos:
  useRootAsPackage: true
```

Child package manifests use:

```yaml
resolution: workspace
```

The root package does not use `resolution: workspace`; Pub rejects that field on the workspace root.

## Dependency changes

- `example/pubspec.yaml` now depends on `agus_design: ^0.0.1`.
- `example/pubspec.yaml` now depends on `agus_maps_flutter: ^0.1.24`; Pub Workspace resolves this to the root package locally.
- `example` lint dependency is aligned to `flutter_lints: ^6.0.0` so the workspace has one compatible lint version.
- `widgetbook/pubspec.yaml` is renamed to package `agus_design_widgetbook`.
- `widgetbook/pubspec.yaml` depends on `agus_design: ^0.0.1` only; it does not depend on `agus_maps_flutter`.
- `packages/agus_design/example/pubspec.yaml` depends on `agus_design: ^0.0.1`.
- The root `pubspec.lock` replaces child workspace lockfiles and should be committed.
- `widgetbook/lib/main.directories.g.dart` is generated by Widgetbook/build_runner and is kept in source so Widgetbook analyzes and runs from a fresh checkout; regenerate it after adding or renaming Widgetbook use cases.

## Example design integration

`example/lib/main.dart` imports `package:agus_design/agus_design.dart` and uses:

```dart
theme: AgusThemeData.light().toThemeData(),
darkTheme: AgusThemeData.dark().toThemeData(),
```

This makes the map example inherit the shared design theme without changing native map setup, asset loading, CoMaps, DuckDB, or platform build logic.

The existing `example/lib/features/workbench/vscode_workbench.dart` overlaps with `AgusWorkbench`, `AgusSidebar`, `AgusViewSection`, `AgusSplitView`, and related components. The safe first pass is theme adoption plus documentation because the current workbench owns map-specific controller state and pane builders. Future refactors can replace local workbench internals with `AgusWorkbench` once the adapter boundary is explicit.

## CI changes

`.github/workflows/devops.yml` now runs workspace setup from the repository root:

```bash
flutter pub get
dart run melos bootstrap
```

This replaces repeated root plus `cd example && flutter pub get` dependency setup. Native build commands still run from repository root, and example app builds still run from `example/` where the Flutter build commands expect platform projects and assets.

## Validation commands

Fast design validation:

```bash
dart run melos run design:analyze --no-select
dart run melos run design:test --no-select
dart run melos run generate --no-select
```

Workspace validation:

```bash
flutter pub get
dart run melos bootstrap
dart run melos list --long
dart run melos run analyze --no-select
```

The default `analyze` script excludes `agus_maps_flutter` and `skin_generator_tool` because those packages already report analyzer info/warning output from native build orchestration code. Design, Widgetbook, design example, and the map example are kept clean.
